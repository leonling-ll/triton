01 / The scheduling gap

The bias has no dot consumer.

The scheduler previously assigned a load only when its recorded consumer was one of the two dots. A separate bias reduction, added after dot 2, fell through that check.

Simplified source · masked edges omitted
for start in tl.range(0, N, 64, num_stages=4):
    k = tl.load(K + offsets(start))
    qk = tl.dot(q, k) / 64
    row_sum = tl.sum(qk, axis=1)
    v = tl.load(V + offsets(start))
    acc = tl.dot(qk.to(tl.float16), v, acc)
    bias = tl.load(Bias + start + lanes)
    acc += tl.sum(bias, axis=0)
    acc += row_sum[:, None] * 0.001

What this branch changes

For loads already selected by the discovery pass, ChainedDotSchedule::scheduleLoads now adds an eligible independent load to STAGE_GLOBAL_LOAD_2: stage 1, cluster 11.

The original “bias between dots” case was already register-pipelined. The new coverage is an independent load whose consumer is outside the two dot operations.
02 / From scheduling to lowering

Follow one bias tile.

The K/V path already uses asynchronous transfers through LDS. The bias stays on the global-memory-to-register path; the change gives its ordinary load a prefetch schedule.

Schedule

The bias load gets loop.stage = 1. Dot 1 remains in stage 2; dot 2 and the consumer remain in stage 3.

Expansion

Two bias loads appear before scf.for. Two bias tensors become loop-carried values, rotated by scf.yield.

Device code

The load remains a buffer load into registers. There is no new bias LDS allocation. Compiler scheduling changes downstream instruction order.

Figure 3. Schedule and final IR are captured from builds of the branch and its exact parent. Expanded excerpts retain compiler SSA names; explanatory comments are added. Full IR and AMD assembly are downloadable below.

Eligibility is intentionally narrow.

  • 01The load must be discovered as a candidate. Unrelated non-dot loads need explicit loop-stage opt-in.
  • 02The load must not be volatile.
  • 03Its pointer, mask and other operands must be independent of carried values, other reads, dots and unsafe operations.
  • 04Writes or unknown effects in the loop block this extra-load optimization.

Earlier loads create an opportunity.

The pass enables memory latency to overlap with computation. It does not guarantee a shorter final instruction schedule. Register allocation, instruction ordering, waits and the selected stage count still matter.

A visible tt.load is not evidence that pipelining failed. Check the prologue and loop-carried values. A prefetched load can remain an ordinary register-producing operation.

This patch does not add general indirect-load analysis or establish optimal scheduling for every attention kernel.

03 / Measured before and after

The load moves earlier.
The kernel runs slower.

The same small workload exposes the lowering change. It also shows why a scheduling fix needs fresh performance validation after a compiler update.

Fresh result on the published branch: 81.481 → 86.842 µs, or 6.58% more latency. The October 27 investigation found a 2.50% reduction on an older compiler. Both results are shown with their own revisions; the historical gain is not attributed to today’s branch.
